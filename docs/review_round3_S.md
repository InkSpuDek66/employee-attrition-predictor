## 1. สรุป

### ใช้ได้ดีไหม

ถ้าใช้เป็น demo กับข้อมูลตัวอย่างของ IBM ระบบใช้ได้ดี ทุกขั้นตั้งแต่ login → ดูภาพรวม → กดดูรายคน → ลองมาตรการใน What-if → ดาวน์โหลด CSV ทำงานครบ ไม่มีหน้าไหนพังในการใช้งานปกติ API ตอบเร็ว (40–135 ms หลังโหลดโมเดลแล้ว) test, lint, สแกน dependency ผ่านหมด และช่องโหว่ใหญ่ 2 ข้อจากรอบก่อน (ไม่มี login, ไม่แยกบริษัท) ปิดไปแล้วจริง ยิงทดสอบแล้วทุกทาง ส่วนที่ต่อ PostgreSQL (นำเข้าไฟล์, batch scoring, cache ของหน้าภาพรวม) ทดสอบกับฐานข้อมูลจริงแล้วก็ทำงานได้ และ test ครบ 32 ข้อผ่าน

ถ้าจะให้บริษัทจริงใช้ ยังไม่พร้อม เหตุผลหลักไม่ใช่โค้ดพัง แต่เป็นตัวเลขและข้อมูลที่ลูกค้าจะไม่เชื่อหรือเอาไปตัดสินใจผิด

- เงินเดือนที่แสดงสูงเกินจริงมาก (มัธยฐาน 172,165 บาท/เดือน) เพราะยังคูณ 35 จาก IBM dataset และ "มูลค่าความเสี่ยงรวม" ขึ้น 974,910,884 บาท สำหรับบริษัท 1,470 คน (DE-01)
- ช่อง "ส่วนต่างถ้ารักษาไว้ได้" เป็นบวกทุกคน แม้คนที่ความเสี่ยง 1/100 ก็ขึ้นตัวเขียวว่าคุ้ม 1.57 ล้านบาท ([UX-15](#ux-15-ตัวเลข-ส่วนต่างถ้ารักษาไว้ได้-ชวนให้ตัดสินใจผิด))
- ตัวเลขบนหน้าภาพรวมดูแม่นเกินจริง เพราะโมเดลให้คะแนนพนักงานที่ใช้เทรนเอง (AUC 0.930 บนหน้าจอ เทียบกับ 0.81 บน test set) (DE-07)
- ประโยคสรุป "สาเหตุหลัก" ยังยกอายุ เพศ สถานภาพสมรส เป็นเหตุผล เจอใน 230 จาก 1,470 คน (UX-06)
- ยังเป็นบัญชีทดลองที่รหัสผ่านอยู่ในหน้า login และใน JavaScript ที่ build แล้ว (SEC-01)

## 2. ขอบเขตและวิธีตรวจ

### ขั้นตอนที่ทำ

1. อ่านโค้ดทุกช่องทางเข้า: `backend/main.py`, `auth.py`, `schemas.py`, `calibration.py`, `model_store.py`, `batch_score.py`, `routers/*.py`, `src/db.py`, `src/business_rules.py`, `src/company_summary.py`, `src/clean_pipeline.py`, `src/feature_pipeline.py`, schema `docker/postgres/init/02-app-schema.sql`, `config/financial_impact.json`, หน้าเว็บ `frontend/src/*.jsx`, `theme.js`, `featureLabels.js`, CI
2. รันชุดตรวจของทีม: `pytest backend`, `ruff check .`, `pip-audit`, `npm audit`, `npm run lint`, `npm test`, `npm run build`
3. ยิง API แบบ in-process ด้วย `TestClient` และ login จริง (ไม่ override auth) ไฟล์ calibration เขียนลงโฟลเดอร์ชั่วคราว ไม่แตะ `backend/calibrations/` ของจริง ([ภาคผนวก A](#a-สคริปต์ยิง-api-แบบ-in-process))
4. ยิง server จริงที่ `127.0.0.1:8000` เฉพาะคำขอที่ไม่แก้ข้อมูล: header ความปลอดภัย, rate limit ของ login ผ่าน `X-Forwarded-For` (ใช้ชื่อผู้ใช้ `nobody`), เวลาตอบระหว่างตรวจไฟล์ 10,000 แถว ([ภาคผนวก B](#b-คำสั่งที่ยิง-server-จริง))
5. ใช้หน้าเว็บจริงผ่าน Playwright (Chromium) ทุกแท็บ ทั้งบัญชี `hr_demo` และ `admin_demo` ที่ขนาดจอ 1440×900, 1366×768, 1440×709 และมือถือ 390×844 ทั้งโหมดสว่างและมืด วัด contrast จากสีที่ browser คำนวณจริง
6. คำนวณตัวเลขที่ลูกค้าเห็นซ้ำจากโมเดลตัวเดียวกับ backend: AUC บนหน้าจอ, เงินเดือนหลังคูณ 35, มูลค่าความเสี่ยง, จำนวนคนที่ข้อมูลส่วนตัวขึ้นเป็นเหตุผล
7. ตรวจ git history หา secret, ตรวจ notebook หา path ในเครื่อง, ตรวจการตั้งค่า GitHub ด้วย `gh api` แบบอ่านอย่างเดียว และลองอ่าน MLflow บน DagsHub โดยไม่ใส่ credential
8. ทดสอบกับ PostgreSQL 17.11 ใน `docker compose`: โหลดข้อมูลด้วย `src/db.py`, รัน `batch_score.py`, รัน `pytest` แบบต่อ DB, เปิด backend ตัวที่สอง (port 8001) และหน้าเว็บตัวที่สอง (port 5174) ที่ต่อ DB แล้วทดสอบนำเข้า ปรับเทียบ และ cache ผ่าน HTTP และหน้าเว็บ ไม่ได้แตะ backend ที่ port 8000 หลังทดสอบลบข้อมูลทดสอบ คืนค่าพนักงาน #1–2 และรัน batch ใหม่ 1 รอบ ([ภาคผนวก E](#e-ทดสอบกับ-postgresql-ใน-docker))

### SEC-14 ตัวจำกัดการ login หลบได้ด้วย header X-Forwarded-For

**ปัญหา** `auth.login_limit` นับครั้งตาม `request.client.host` แต่ uvicorn เปิด proxy headers เป็นค่าเริ่มต้นและเชื่อ `X-Forwarded-For` จาก `127.0.0.1` คำขอที่มาจากเครื่องเดียวกัน (รวมคำขอที่ผ่าน Vite proxy) จึงตั้ง IP ของตัวเองได้

**หลักฐาน** ยิง server จริง 13 ครั้งด้วยรหัสผิด ใส่ `X-Forwarded-For: 10.9.8.1` ถึง `10.9.8.13` ได้ 401 ทั้ง 13 ครั้ง ไม่มี 429 เลย ส่วนกลุ่มควบคุมที่ใส่ค่าเดิม `10.9.9.9` ทุกครั้งได้ 429 ตั้งแต่ครั้งที่ 11 แปลว่า key ของ limiter คือค่าที่ผู้ส่งกำหนดเอง

**ทำไมต้องแก้** ตอนนี้รหัสผ่านทดลองเปิดเผยอยู่แล้ว ผลกระทบจึงต่ำ แต่เมื่อมีผู้ใช้จริง rate limit นี้คือด่านเดียวที่กันการเดารหัส อีกด้านหนึ่ง ถ้า deploy หลัง reverse proxy แล้วไม่ได้ตั้ง `--forwarded-allow-ips` ให้ถูก ทุกคนจะใช้ IP ของ proxy ร่วมกัน คนเดียวกดผิด 10 ครั้งก็ล็อกทั้งบริษัทได้ 1 นาที

**วิธีแก้**
1. รัน uvicorn ด้วย `--forwarded-allow-ips` ที่ระบุ IP ของ proxy จริงเท่านั้น (ตอน dev ใช้ `--no-proxy-headers`) และเขียนไว้ใน run guide
2. นับเพิ่มอีกชั้นตามชื่อผู้ใช้ (เช่น 5 ครั้งผิดต่อ 15 นาทีต่อบัญชี) ไม่พึ่ง IP อย่างเดียว
3. เมื่อรันหลาย worker/เครื่อง ย้ายตัวนับไป Redis หรือ rate limit ที่ proxy (ตามที่ `auth.py` เขียนไว้แล้ว)

**เสร็จเมื่อ** test ส่ง `X-Forwarded-For` ต่างกัน 11 ครั้งแล้วได้ 429 และมี test ล็อกตามชื่อผู้ใช้

### SEC-15 ตรวจไฟล์นำเข้าทำให้ API ทั้งระบบค้าง

**ปัญหา** `validate_upload` และ `import_employees` เป็น `async def` แต่งานข้างใน (pandas อ่านไฟล์ + pydantic ตรวจทีละแถว) เป็น CPU ล้วน และตอนบันทึกยังเขียน DB ด้วย psycopg แบบ sync ไม่มี `await` ระหว่างทาง event loop จึงหยุดรับงานอื่นจนกว่าจะเสร็จ และ `/employees/validate` ไม่มี rate limit (มีแค่ `/employees/import`)

**หลักฐาน** บน server จริง ระหว่างตรวจ CSV 10,000 แถว (1.4 MB, ใช้ 2.46 วินาที) คำขอ `/auth/me` ที่ส่งตามไปติดรอ 1.91 วินาที ปกติตอบใน 0.012 วินาที แบบ in-process ตรวจ 10,000 แถวใช้ 0.7–1.9 วินาที แล้วแต่รอบ ตอนต่อ PostgreSQL บันทึก 10,000 แถวผ่าน `/employees/import` ใช้ 3.2 วินาที และ `/auth/me` ที่ส่งระหว่างนั้นติดรอ 2,378 ms

**ทำไมต้องแก้** ผู้ใช้ HR คนเดียวอัปโหลดไฟล์ใหญ่วนไปเรื่อยๆ ก็ทำให้ทุกคนในระบบใช้งานไม่ได้ และแม้ไม่ได้ตั้งใจ แค่มีคนตรวจไฟล์ หน้า What-if ของคนอื่นก็กระตุก

**วิธีแก้**
1. เปลี่ยนเป็น `def` ธรรมดา (FastAPI จะรันใน threadpool ให้) หรือเรียกส่วนตรวจผ่าน `await run_in_threadpool(...)`
2. ใส่ `auth.LIMITS["import"].per_user` (หรือ limit แยก) ให้ `/employees/validate` ด้วย

**เสร็จเมื่อ** ระหว่างตรวจไฟล์ 10,000 แถว `/auth/me` ยังตอบในไม่เกิน 100 ms และ validate ครั้งที่ 21 ใน 1 นาทีได้ 429

### SEC-16 token ที่มีอักขระนอก ASCII ทำให้ server ตอบ 500

**ปัญหา** `read_token` ใน `backend/auth.py` เรียก `hmac.compare_digest(sig, _sign(payload))` ด้วย `str` ถ้าส่วน signature มีอักขระนอก ASCII ฟังก์ชันนี้ raise `TypeError` ซึ่งไม่มีใครจับ

**หลักฐาน** `Authorization: Bearer abc.ไทย` ได้ `500 Internal Server Error` (ส่วน payload ที่เป็นภาษาไทยได้ 401 ตามปกติ)

**ทำไมต้องแก้** ไม่ได้ทำให้เข้าระบบได้ แต่คนที่ยังไม่ login ทำให้ server เขียน stack trace ลง log ได้ไม่จำกัด และ monitor จะนับเป็น error ของระบบ

**วิธีแก้** เทียบเป็น bytes: `hmac.compare_digest(sig.encode("utf-8", "surrogateescape"), _sign(payload).encode())` หรือเช็ก `sig.isascii()` ก่อนแล้วคืน `None`

**เสร็จเมื่อ** test ส่ง token ที่มีอักขระไทยในทั้งสองส่วนแล้วได้ 401

### SEC-17 ออกจากระบบแล้ว token ยังใช้ได้ 8 ชั่วโมง

**ปัญหา** ปุ่มออกจากระบบลบ token ใน `sessionStorage` อย่างเดียว ฝั่ง server ไม่มีรายการ token ที่ยกเลิกแล้ว token ที่ถูกคัดลอกไปจึงใช้ได้จนหมดอายุ (`TOKEN_TTL = 8 * 3600`)

**หลักฐาน** ดูจากโค้ด `auth.py` (ไม่มี endpoint logout) และ `App.jsx` (`onLogout` เรียกแค่ `saveSession(null)`) ทดสอบหน้าเว็บแล้ว: กดออกจากระบบแล้วกด back กลับไปหน้า login ถูกต้อง ฝั่งหน้าเว็บจึงไม่มีปัญหา

**ทำไมต้องแก้** เครื่องที่ใช้ร่วมกันในฝ่าย HR เป็นเรื่องปกติ ถ้า token หลุด (เช่นจาก log ของ proxy) ไม่มีทางตัดได้

**วิธีแก้** ทำพร้อม SEC-01 ตอนย้ายผู้ใช้ไปตาราง `users`: เก็บ `token_version` ต่อผู้ใช้ใส่ใน token แล้ว logout = เพิ่มเลข หรือลด TTL เหลือ 1–2 ชั่วโมงพร้อม refresh

**เสร็จเมื่อ** เรียก logout แล้วใช้ token เดิมได้ 401

### SEC-18 แอปต่อ PostgreSQL ด้วย superuser

**ปัญหา** `docker-compose.yml` ตั้ง `POSTGRES_USER: attrition` ซึ่ง image ของ postgres สร้างเป็น superuser และ `DATABASE_URL` ที่ run guide แนะนำก็ใช้ user นี้ backend, `batch_score.py`, `src/db.py` และ MLflow (database `mlflow`) จึงใช้สิทธิ์สูงสุดตัวเดียวกันทั้งหมด

**หลักฐาน** ต่อด้วย `DATABASE_URL` ตาม run guide แล้ว `select rolsuper from pg_roles where rolname = current_user` ได้ `t`

**ทำไมต้องแก้** ตอนนี้ SQL ทุกตัวใช้ parameter ยังไม่เจอ SQL injection แต่ถ้าวันหนึ่งมีช่องโหว่หรือ backend ถูกยึด superuser ลบได้ทุกตาราง อ่าน database `mlflow` ได้ และใช้ `COPY ... TO PROGRAM` รันคำสั่งในเครื่อง DB ได้ ข้อมูลพนักงานทุกบริษัทอยู่ในตารางเดียวกัน ความเสียหายจึงกว้าง

**วิธีแก้** เพิ่ม init script สร้าง role แยก: role ของ backend ให้ SELECT/INSERT/UPDATE เฉพาะตารางที่ใช้ (ไม่มี DDL), role ของ batch ให้ INSERT ตารางผลทำนาย และใช้ superuser แค่ตอนสร้าง schema บนคลาวด์ใช้ user ที่ไม่ใช่เจ้าของ database และพิจารณา Row Level Security ตาม `tenant_id` เมื่อมีหลายบริษัท (ต่อจาก SEC-10)

**เสร็จเมื่อ** user ใน `DATABASE_URL` ของ backend ได้ `rolsuper = f` และสั่ง `DROP TABLE employees` ไม่ได้

### DE-10 ตัวตรวจไฟล์นำเข้ากับ CHECK ของฐานข้อมูลไม่ตรงกัน

**ปัญหา** `schemas.EmployeeInput` รับอายุ 15–100 แต่ตาราง `employees` ใน `02-app-schema.sql` มี `CHECK (age BETWEEN 15 AND 80)` ไฟล์ที่มีคนอายุ 81–100 จึงผ่านขั้นตรวจ ปุ่ม "บันทึกเข้าระบบ" กดได้ แล้วตอนบันทึกฐานข้อมูลปฏิเสธทั้งไฟล์ด้วยข้อความรวมๆ ว่า "มีค่าบางแถวเกินช่วงที่ฐานข้อมูลรับ" โดยไม่บอกว่าแถวไหน

**หลักฐาน** อัปโหลดไฟล์ที่แถวหนึ่งอายุ 85 ผ่านหน้าเว็บ ได้ผลว่าแถวนั้นผ่านและอยู่ในตัวอย่างแถวที่ผ่าน (ยิง in-process อายุ 95 ก็ผ่าน) ทดสอบกับ PostgreSQL จริง: `/employees/validate` ตอบว่าผ่าน 1 แถว ไม่มี error แต่ `/employees/import` ไฟล์เดียวกันได้ 422 "มีค่าบางแถวเกินช่วงที่ฐานข้อมูลรับ (เช่น อายุ 15–80 ปี) ยังไม่ได้บันทึกอะไร ตรวจไฟล์แล้วลองใหม่" และไม่มีแถวไหนถูกบันทึก ทีมรู้เรื่องนี้อยู่แล้ว (`test_db.py` ทดสอบไว้ว่าต้องปฏิเสธทั้งไฟล์) ที่ขาดคือผู้ใช้ไม่รู้ว่าแถวไหน

**ทำไมต้องแก้** ผู้ดูแลระบบจะไม่รู้ว่าต้องแก้แถวไหน ต้องเดาเอง และกฎเดียวกันอยู่ 2 ที่ซึ่งจะเพี้ยนต่อไปเรื่อยๆ

**วิธีแก้** ให้ `schemas.py` เป็นต้นฉบับ: ปรับ `Age` เป็น `le=80` (หรือแก้ CHECK ให้ตรง แล้วแต่ทีมตกลง) และเพิ่ม test ที่อ่านช่วงค่าจาก schema SQL มาเทียบกับ `EmployeeInput` แบบเดียวกับ test เกณฑ์ระดับความเสี่ยง

**เสร็จเมื่อ** ไฟล์ที่อายุ 85 ไม่ผ่านขั้นตรวจ และ error บอกเลขแถวกับคอลัมน์

**หลักฐาน** ปรับเทียบแบบ isotonic ด้วยข้อมูล IBM 300 แถว แล้วเปิดหน้าภาพรวม: การ์ดยังบอกเสี่ยงสูง 185 คน (High 185 / Medium 274 / Low 1,011) แต่รายชื่อ 100 อันดับแรกขึ้น "สูง" ทั้ง 100 คน · พนักงาน #19 ใน `/shap` ได้ 1.000 ส่วน `/whatif` ที่ไม่ส่ง `tenant_id` ได้ 0.957 พร้อมคำเตือนว่ายังไม่ปรับเทียบ หน้าเว็บตอนนี้ส่ง `tenant_id` เองจึงยังไม่เห็นข้อหลัง แต่ Superset หรือ client อื่นจะเห็น

ใน PostgreSQL ก็เป็นแบบเดียวกัน: หลังปรับเทียบแล้วรัน `batch_score.py` รอบเดียว ตาราง `attrition_predictions` ได้ High 168 / Medium 106 / Low 1,196 แต่ `company_risk_summary` ของรอบเดียวกันได้ High 185 / Medium 274 / Low 1,011 และหน้าภาพรวมที่ต่อ DB แสดงคะแนนเฉลี่ย 33 กับเสี่ยงสูง 185 คน ขณะที่รายชื่อด้านล่างขึ้น 100 ติดกัน 4 คนแรก

**ทำไมต้องแก้** เมื่อบริษัทปรับเทียบแล้ว ตัวเลขบนหน้าเดียวกันจะขัดกันเอง Superset ที่อ่าน 2 ตารางจะได้จำนวนคนเสี่ยงสูงไม่ตรงกับหน้าเว็บ และ README 6.5 ตั้งใจให้ใช้คะแนนปรับเทียบเมื่อมี

**วิธีแก้**
1. `predict`, `whatif`, `financial_impact` ใช้ `user["tenant_id"]` จาก token เหมือน `/shap` (ฟิลด์ `tenant_id` ใน request เหลือไว้แค่ให้ guard ตรวจ หรือเลิกรับ)
2. `company_summary.summarize` รับคะแนนที่แสดงจริง (ปรับเทียบถ้ามี) ทั้งใน router และ `batch_score.py` หรือถ้าทีมอยากให้ภาพรวมใช้คะแนนดิบ ต้องเขียนกำกับบนการ์ดว่า "ยังไม่ปรับเทียบ"
3. `_cached` ต้องรู้ว่า cache สร้างก่อนหรือหลังการปรับเทียบครั้งล่าสุด

**เสร็จเมื่อ** test ที่ปรับเทียบแล้วเช็กว่าจำนวน High จาก `/company-summary` เท่ากับจำนวนคนที่ `risk_band == "High"` เมื่อดึงทุกคน และ `/whatif` ที่ไม่ส่ง `tenant_id` ได้คะแนนเดียวกับ `/shap`

### DE-15 ข้อมูลพนักงานค้างใน memory ของ backend จนกว่าจะ restart

**ปัญหา** `model_store.raw_employees()` และ `employee_features()` ใช้ `lru_cache` ที่ไม่มีวันหมดอายุ ล้างได้ทางเดียวคือ `/employees/import` ใน process เดียวกัน ข้อมูลที่เปลี่ยนทางอื่น (รัน `src/db.py` ใหม่, แก้หรือลบด้วย SQL, import ผ่าน worker อีกตัว) backend จะไม่เห็นจนกว่าจะ restart

**หลักฐาน** ลบพนักงานทดสอบ 10,010 คนออกจาก DB ด้วย SQL แล้วเรียก backend ที่ยังเปิดอยู่: `/shap/100001` ยังได้ 200 และรายชื่อเสี่ยงสูงยังนับคนที่ถูกลบไปแล้ว ส่วนการ์ดบนหน้าภาพรวมอ่าน cache ใน DB ซึ่งไม่มีคนเหล่านั้น หน้าเดียวกันจึงใช้ข้อมูลพนักงานคนละชุด

**ทำไมต้องแก้** การลบหรือแก้ข้อมูลตามคำขอของเจ้าของข้อมูล (PDPA) ต้องมีผลทันที ไม่ใช่รอ restart และเมื่อ deploy แบบหลาย worker ผู้ใช้จะเห็นข้อมูลไม่เท่ากันแล้วแต่ว่า request ไปตก worker ไหน

**วิธีแก้** เก็บ "เวอร์ชันข้อมูล" ต่อบริษัท (เช่น `max(updated_at)` กับจำนวนแถว ซึ่ง query เร็วมาก) แล้วให้ cache ตรวจทุก request หรือทุก 30 วินาที ทำนองเดียวกับที่ `_cached` ของ `/company-summary` ทำอยู่แล้ว ถ้าต้องลบจริงให้เพิ่ม trigger ที่อัปเดตเวอร์ชันด้วย

**เสร็จเมื่อ** test ลบพนักงานด้วย SQL แล้ว `/shap/{id}` ได้ 404 โดยไม่ต้อง restart

### DE-16 batch scoring เก็บทุกรอบไม่มีการลบ

**ปัญหา** `batch_score.py` เพิ่มผลทุกรอบโดยไม่ลบของเก่า (ตามที่ docstring ตั้งใจ) และเก็บ SHAP ครบทุกฟีเจอร์ของทุกคน

### UX-13 เมนูซ้ายหายบนจอโน้ตบุ๊ก

**ปัญหา** แถบซ้ายบนจอใหญ่ (`lg:`) เป็น flex column ที่ตัวการ์ตูน (`Mascot`, `flex-1`) แย่งพื้นที่กับเมนู เมนูถูกบีบจนเหลือกล่องเลื่อนเล็กๆ

**วิธีแก้** ให้ `nav` เป็น `shrink-0` (ไม่ยอมถูกบีบ) และให้ส่วนการ์ตูนเป็น `min-h-0 overflow-hidden` หรือซ่อนการ์ตูนเมื่อจอเตี้ย เช่น `[@media(max-height:820px)]:hidden`

**เสร็จเมื่อ** ที่ viewport 1366×650 เห็นแท็บครบ 4 อันโดยไม่ต้องเลื่อน

### UX-14 หน้าภาพรวมล้นจอแนวนอนบนมือถือ

**ปัญหา** ที่ความกว้าง 390px การ์ด "พนักงานเสี่ยงสูงสุด 10 คน" และ "ปัจจัยที่ทำให้เสี่ยงมากที่สุด" กว้าง 461px เพราะ grid item ใน `grid ... xl:grid-cols-2` มี `min-width: auto` ตามค่าเริ่มต้น เนื้อหาข้างในจึงดันการ์ดให้กว้างเกินจอ

### UX-15 ตัวเลข "ส่วนต่างถ้ารักษาไว้ได้" ชวนให้ตัดสินใจผิด

### UX-16 ข้อความและสถานะในหน้านำเข้าข้อมูลสำหรับผู้ดูแลระบบ

**ปัญหา** ลองใช้ในบทบาทผู้ดูแลระบบแล้วสะดุด 5 จุด

**วิธีแก้** ให้ `/auth/me` (หรือ endpoint สถานะ) บอกว่า DB พร้อมไหม แล้วซ่อนปุ่มพร้อมข้อความ "ติดต่อผู้ดูแลระบบเพื่อเปิดการบันทึก", ย้าย error ของการบันทึกไปไว้ข้างปุ่ม, ตัดจุลภาคและช่องว่างในช่องตัวเลขก่อนตรวจ, แสดงค่าตามที่ผู้ใช้กรอก

### UX-18 บันทึกไฟล์แล้วหน้าอื่นไม่อัปเดตจนกว่าจะรีเฟรช

**ปัญหา** ทุกแท็บถูก mount ค้างไว้ (ซ่อนด้วย `hidden`) และ `useApi` ใน `Overview.jsx` โหลดใหม่เฉพาะตอน path เปลี่ยน หลังผู้ดูแลระบบบันทึกไฟล์ หน้าอื่นจึงยังแสดงข้อมูลเก่า

**หลักฐาน** ทดสอบกับ backend ที่ต่อ PostgreSQL: บันทึกพนักงานใหม่ 5 คนผ่านหน้าเว็บได้ "บันทึกแล้ว: เพิ่มใหม่ 5 คน อัปเดต 0 คน" กดกลับไปแท็บภาพรวมยังเห็น 1,470 คน / เสี่ยงสูง 185 คน ต้องรีเฟรชทั้งหน้าถึงเป็น 1,475 คน / 190 คน

**ทำไมต้องแก้** ผู้ดูแลระบบจะคิดว่าบันทึกไม่สำเร็จแล้วอัปโหลดซ้ำ หรือเอาตัวเลขเก่าไปรายงาน

**วิธีแก้** เก็บตัวนับ `dataVersion` ใน `App.jsx` เพิ่มทุกครั้งที่บันทึกสำเร็จ แล้วใส่ใน key ของ `useApi` และ `TopRiskList` ให้ทุกแท็บโหลดใหม่ พร้อมข้อความสั้นๆ ว่าข้อมูลอัปเดตแล้ว

**เสร็จเมื่อ** บันทึกไฟล์แล้วกลับไปหน้าภาพรวมเห็นจำนวนใหม่ทันทีโดยไม่ต้องรีเฟรช

## 7. จุดที่ทำได้ดี (ควรรักษาไว้)

- ปิดช่องโหว่ใหญ่ของรอบก่อนได้จริง ไม่ใช่แค่ติ๊ก checkbox: ยิงลองหลบ tenant guard 5 แบบแล้วไม่ผ่านสักแบบ
- ป้องกันข้อมูลขนาดใหญ่ครบทั้ง Content-Length, chunked และ zip bomb ของ xlsx ซึ่งเป็นจุดที่โปรเจกต์ส่วนใหญ่ลืม
- log ไม่มีข้อมูลพนักงาน: `/recalibrate` log แค่ชนิด error, `db.IntegrityError` เก็บแค่ชื่อ constraint
- token เก็บใน `sessionStorage` และส่งทาง header ไม่มี cookie จึงไม่ต้องกังวลเรื่อง CSRF และไม่มี CORS เปิดกว้าง
- หน้าตรวจไฟล์นำเข้าเขียนสำหรับ HR ไทยจริง: หัวคอลัมน์ไทย รับค่าไทย บอกเลขแถวตาม Excel
- หน้า What-if: มาตรการสำเร็จรูป, บันทึกผลเทียบ, แสดงสูตรที่มาของตัวเงิน, แถบผลติดขอบล่างบนมือถือ
- สถานะโหลด/ไม่พบ/ระบบพังครบทุกแท็บ ลิงก์แชร์ได้และปุ่ม back ใช้ได้
- CI รัน lint, test, เทรนซ้ำ, สแกนช่องโหว่ ทั้ง Python และ npm และผ่านทั้งหมดบน commit ล่าสุด · ไม่มี secret ใน git history
- test ที่กันเกณฑ์ระดับความเสี่ยงไม่ตรงกันระหว่าง Python กับ JavaScript (`test_business_rules.py`) เป็นแนวที่ควรใช้กับ DE-10 ด้วย
- ส่วน PostgreSQL: schema สร้างเองตอนเปิด compose, SQL ใช้ parameter ทุกที่, PostgreSQL เปิดให้แค่ `127.0.0.1`, นำเข้าแบบทั้งไฟล์หรือไม่บันทึกเลย, cache ของหน้าภาพรวมรู้เองว่าข้อมูลพนักงานใหม่กว่า และ test ของ DB เก็บกวาดข้อมูลตัวเอง
